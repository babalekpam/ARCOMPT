---
name: Managed Publish schema round trips
description: Limits observed when Replit's managed Publish flow introspects this project's PostgreSQL schema.
---

Inspect the generated development-to-production SQL whenever publishing custom database constraints or security objects. A bare boolean check can be emitted as invalid nested `CHECK (CHECK (...))`; an equivalent explicit boolean expression such as `IS TRUE` round-trips correctly.

**Why:** The development constraint was valid, but publish-time introspection generated invalid SQL. Separately, the observed diff omitted conditions from row-level-security policies and did not include custom database functions, even though those existed in development. A syntactically valid diff alone therefore does not prove equivalent access control or runtime behavior. Copying missing SECURITY DEFINER functions is not a safe repair by itself: function ownership and cross-tenant EXECUTE grants must match the intended privilege boundary, especially when the managed owner has BYPASSRLS. Two draft repairs failed review because missing group roles also meant missing historical table/sequence grants, and a disposable rehearsal cannot be inferred safely from a URL's name.

**How to apply:** Compare generated policy definitions, function availability, ownership, privileges, and triggers with development before authorizing a live publish. Treat the Publish-generated SQL as a pre-Publish input for the disposable rehearsal, not as a post-Publish repair to run a second time. For SQL rehearsal, require an explicit disposable database target and assert its catalog shape; never fall back to the ordinary database URL or trust a string heuristic to exclude production. Review every historical grant when a role is absent. Never compensate by injecting production DDL into build or startup steps.

Replit documentation distinguishes the user's manual production SQL runner from Agent's read-only production access. A semantic documentation search once suggested manual Agent DDL despite the actual production-database page saying Agent cannot modify production; consult the full page and the database skill before acting. A Reserved VM's runtime filesystem is not durable across replacement or republish, so self-hosting PostgreSQL on that VM is not a safe shortcut around the managed Publish diff.

For catalog comparisons across Publish and a synthetic local cluster, compare columns by **name**, not physical attribute position, and exclude extension-owned function definitions from application-function fingerprints. A local PostgreSQL 16 instance may lack pgvector and therefore omit its optional embedding column and extension functions.

**Why:** The published and development column definitions matched while the disposable migration replay placed audit columns in a different physical order. The local PostgreSQL distribution also lacked pgvector, making an otherwise-correct whole-schema function fingerprint differ by hundreds of extension functions. Neither difference changed the application security contract.

**How to apply:** Fingerprint all comparable application-owned constraints, indexes, triggers, RLS, PUBLIC grants and non-extension functions; explicitly account for known Publish gaps and optional extensions. Require exact production baseline preflight before applying a reviewed repair, then test with actual restricted logins, not a privileged owner session.
